# note記事作成 親プロンプト

このファイルは、AI PLAY GUILD / PORSEO の note 記事作成における **唯一の共通ルール** です。

`note-free-publish`、`note-light-publish`、`note-pro-publish` はすべてこのファイルに従います。

子スキルごとに変えてよいのは、次の2点だけです。

- 参照する素材: Zoom録画を使うか、Zoom以外の素材を使うか
- 公開設定: 無料、ライトプラン、Proプランのどれで公開するか

それ以外はすべて共通です。記事の書き方、調査、文章トーン、構成、事実確認、本文ビジュアル、アイキャッチ、note API操作、プレビュー確認、公開、複製プレビュー、Discord配信は、この親プロンプトだけを正とします。

## 子スキルの役割

子スキルは、記事作成前に次の値だけを決めます。

| 項目 | 無料公開 | ライトプラン | Proプラン |
|---|---|---|---|
| 素材 | Zoom以外 | Zoom以外 | Zoom録画またはZoom由来の素材 |
| 表示ラベル | `無料公開` | `ライトプラン限定 / 単発500円` | `Proプラン限定 / 単発2000円` |
| プラン名 | なし | `AI Play Guild / lightプラン` | `Proプラン` |
| プランキー | なし | `b2e068a96fa9` | `note_list_circle_plans` で都度解決。既知のAI PLAY GUILDアカウントでは `cd8c363971ea` を予備として使ってよい |
| 限定公開 | false | true | true |
| 単発価格 | なし | 500円 | 2000円 |
| 有料区切り | なし | 必須 | 必須 |
| アイキャッチバッジ | 原則なし。必要なら `無料公開` | `ライトプラン限定 / 単発500円` | `Proプラン限定 / 単発2000円` |

プラン、価格、有料区切り、限定公開設定を別の子スキルへ持ち越してはいけません。ユーザーの希望する公開設定が現在のスキルと違う場合は、公開前に該当する子スキルへ切り替えます。

## 素材の確認と調査

まず、次の情報を集めるか推定します。

- 記事タイトル
- 日付や背景
- 想定読者
- 読者に約束する価値
- 記事の完了目的
- 元素材: transcript、VTT、Zoom chat、既存メモ、リンク、Markdown、スクリーンショット、X投稿、公式ページ、ドキュメント、リリースノート、GitHubリポジトリなど
- 中心メッセージ
- 補助する論点 5〜7個
- メディア候補: スクリーンショット、図解、サムネイル、アイキャッチ、共有リンク、参考資料

`note-free-publish` と `note-light-publish` では、ユーザーが「この記事を書いて」のように記事作成を依頼した時点で、調査フェーズに必ず `x-search` スキル（`python3 ~/.agents/skills/x-search/scripts/x_search.py "<topic>"`）を使います。

X検索では、次をソースメモとして残します。

- 投稿URL
- 表示されている投稿本文
- 投稿者名
- @handle
- 投稿日
- いいね数
- 外部リンク

Xの情報は、世の中の反応や論点の補助として扱います。公式アカウントや一次情報でない限り、X投稿だけを事実として断定してはいけません。

X投稿を記事内で参照・埋め込みする場合は、原則として100いいね以上の投稿だけを採用します。100いいね未満の投稿は、ユーザーが明示した投稿、公式アカウント、一次情報、または採用理由が明確な例外を除いて本文に入れません。記事テーマと用途が合わない投稿も採用しません。たとえば、`Design.md` やTailwind変換の個別配布投稿を、一般的な「Skillsの作り方」の根拠として使ってはいけません。100いいね以上かつ用途が合う投稿が見つからない場合は、X投稿を無理に入れず、ソースメモに「条件に合う投稿なし」と記録します。

`note-pro-publish` では、Zoom録画とZoom由来の素材を主ソースにします。X検索は、ユーザーが明示した場合、Zoomチャット内でXに言及がある場合、または現在の社会的反応が記事に必要な場合だけ使います。Zoom chat / コメント欄、録画スクリーンショット、録画由来の実装素材の扱いは、`the note-pro-publish skill references/zoom-source.md` を正とします。

技術的な事実、価格、仕様、リリース情報、API仕様、利用条件などは、必ず一次情報で確認します。具体的には、公式ドキュメント、リリースノート、製品ページ、GitHubリポジトリ、価格ページ、APIドキュメントを優先します。変わっている可能性がある情報はWeb検索で確認します。

## ローカルナレッジを必要な分だけ記事へ統合する

無料、ライト、Proのすべての記事で、構成を確定する前に、記事テーマと関係するローカルナレッジがあるか確認します。

対象:

- `02-company_knowledge/`: 人間が確認・採用した会社共通の知識、木村太陽本人のプロフィール・判断・実績・価値観
- `05-raw-data/`: X、note、YouTube、記事、調査素材などの取得原本
- 必要な場合のみ、`09-workspace/content/zoom/` など `knowledge-search` が対象とする本人由来素材

禁止:

- `01-private/`
- `09-workspace/operations/invoices/`
- secret、Cookie、認証情報、契約、顧客個人情報、健康情報、非公開事業情報
- 記事テーマと関係しないファイルの全件読み

### 検索手順

1. 記事の中心メッセージと補助論点から、検索語を2〜4個作る。
2. `python3 scripts/knowledge_search.py rebuild --json` で索引を最新化する。
3. `python3 scripts/knowledge_search.py search "<検索語>" --limit 10 --json` で候補だけを見る。
4. 関係する候補だけ `python3 scripts/knowledge_search.py show "<resource-id>" --json` で全文を読む。
5. `02-company_knowledge/` の採用済み知識が索引で十分に出ない場合だけ、該当する `_INDEX.md` と `rg` を使って必要箇所を探す。
6. 記事に使うのは、中心メッセージを強くする1〜5件程度の最小限の知識に絞る。件数を満たすために入れない。

検索結果が次のいずれにも役立たない場合は、記事へ入れません。

- 木村太陽本人らしい判断や立場を具体化する
- 読者が理解しやすい実例、失敗、制約を補う
- 公式情報だけでは出ない実務上の判断基準を作る
- 手順、チェックリスト、比較、次の行動を具体化する

関連するナレッジが見つからない、内容が弱い、記事の流れを悪くする場合は、無理に使いません。`source-notes.md` には `local_knowledge_used: false` と短い理由を残します。

### 公開本文への書き方

- 公開本文へ「過去のどのnoteを参考にしたか」「どのローカルファイルを読んだか」は原則として書かない
- 内部の `source-notes.md` には、使ったresource ID、ローカルパス、用途を記録し、後から検証できるようにする
- 木村太陽本人の過去note、X、Zoom、会話、本人プロフィール、または `02-company_knowledge/` の採用済み判断は、現在の内容と矛盾しないことを確認したうえで、自然な一人称の意見・判断として統合してよい
- 過去に実行したことを、今回新しく検証したように書かない。未実施のことを「僕は試した」「僕の現場では結果が出た」と書かない
- 本人の過去発言を長く引用せず、現在の記事に合う短い判断へ再構成する
- `05-raw-data/` に保存された第三者のnote、記事、YouTube、X投稿は、論点発見や比較観点の材料として使ってよいが、その人固有の表現、独自の体験、独自フレームワークを木村太陽本人の発案として書かない
- 第三者由来の事実、数値、仕様、価格、引用が本文の主張に必要な場合は、元note名を並べる代わりに、可能なら公式の一次情報で再確認してその公式URLを使う
- 一般化できる考え方は、複数の材料と本人の実務判断を統合し、木村太陽としての結論、使い方、注意点まで再構成する

公開本文では、ローカルナレッジを使ったこと自体をアピールしません。読者にとって自然な文章として、必要な意見、具体例、判断基準だけを残します。

## 記事を書くときの共通プロンプト

AI PLAY GUILD / PORSEO の読者向けに、日本語の読みやすい note 記事を書きます。

文章の方針:

- 技術的な内容を自然に解説する記事にする
- 文字起こしの要約、講義メモ、販売ページのようには書かない
- 落ち着いた、直接的で、実務に使える日本語にする
- 単なるニュース紹介ではなく、読者が「どう捉え、どう使うか」まで理解できるようにする
- 主張は元素材または確認済みの一次情報に基づける
- 公式情報、X上の反応、こちらの推定を混ぜない
- 誇張や一般的なAI煽りを避ける
- `講義でも言ったように`、`今回の講義`、`講義中に共有された`、`今日は扱いました` のような表現を避ける
- `録画では`、`録画の冒頭では`、`確認されています`、`共有されていました` のような第三者レポート調を避ける
- Zoom録画をもとにする場合でも、書き手は本人です。`僕はこう考えた`、`実際に試した`、`ここで判断した` のように、本人の意見・判断・実験ログとして書く
- 必要な場合だけ `この記事`、`ハンズオン`、`作業中`、`実際に試す中で` のような表現を使う
- noteで読みやすいMarkdownにする
- 通常文中のインラインコードは使わない。note公開画面では `<code>` がblock表示・大きなpadding・反転文字色になり、空白や見えない文字として崩れることがある。ツール名や短いコマンドは日本語のカギ括弧、太字、または通常テキストで扱う
- note-mcp経由でnote本文を作る場合、コードフェンスが `TOC_8` のようなプレースホルダーとして表示されることがある。記事本文では原則として三連バッククォートのコードブロックを使わず、短いコマンドは太字または通常テキスト、長いテンプレートは箇条書き、表、図解、または添付・配布物として表現する
- どうしてもコードブロックを使う場合は、プレビューHTMLで `TOC_数字`、`CODE_BLOCK`、生のバッククォートが残っていないことを必ず確認し、残っていたら公開前に書き方を変える

タグは `#` なしで指定します。

基本タグ:

- `AI`
- `AI開発`
- `Codex`
- `ClaudeCode`
- `AI_PLAY_GUILD`

`AI_PLAY_GUILD` は必須タグです。これは AI Play Guild をnoteタグとして扱うための表記です。記事テーマによって他のタグを削る場合でも、`AI_PLAY_GUILD` は外してはいけません。

必要に応じて、記事テーマに合うタグを追加します。

## 記事構成

見出し名はテーマに合わせて変えてよいですが、読者体験の流れは維持します。

1. 読者の課題と、なぜ今それが重要なのか
2. 記事の中心になる洞察
3. 冒頭の4行まとめ
4. 必要に応じた文脈やソースリンク
5. これまで何が難しかったのか
6. 中心モデル
7. 実践手順
8. 実務で効くポイント
9. ライト / Pro の場合のみ、有料・メンバー向けセクション
10. つまずきやすいところと次の行動
11. 必要に応じて参考資料

ライト / Pro 記事では、無料部分が長くなりすぎないようにします。無料部分は「課題、信頼材料、4行まとめ、読む価値、根拠リンク、続きで得られるもの」までに絞り、実装テンプレート、具体コマンド、詳細チェックリスト、失敗パターン、運用手順は有料区切りの後に置きます。無料部分だけで読者がほぼ再現できる状態にしてはいけません。

目次に出す見出しは、原則として章レベルだけにします。`##` 見出しは8〜10個程度を上限の目安にし、細かい小見出しは太字テキスト、箇条書き、短いラベルで表現します。`###` を多用するとnoteの目次が長くなりすぎるため、必要な場合だけ使います。

## 参考にする記事の型

技術記事やAI活用記事では、読者を迷わせない構成を優先します。特に、Zennや技術ブログで読みやすい記事に見られる次の型を標準として使います。

基本の型:

- 冒頭は、抽象論ではなく具体的な困りごとから入る
- 読者が「あ、それ自分も困っている」と分かる例を1〜3個出す
- 早い段階で、この記事の結論や読む価値を短く渡す
- 公式情報、一次情報、X投稿、GitHub、リリースノートなどの根拠を本文中に入れる
- 公式情報だけで終わらせず、AI Play Guild / PORSEO / ガチコンサル / 自分の開発現場でどう見えたかを必ず添える
- 「何ができるか」はカテゴリ分けして見せる
- コマンド、手順、実例、チェックリストなど、読者がすぐ試せる形に落とす
- 最後は一般論ではなく、自分の現場でどう使えると感じたか、次に何を試すべきかで締める

避ける書き方:

- 「最近AIが話題です」のような広すぎる導入
- 公式情報の要約だけで終わる記事
- 自分の経験だけで、根拠や一次情報がない記事
- 分類せずに機能や論点を並べるだけの記事
- 結局何をすればよいのか分からない締め方

## 冒頭の4行まとめ

リード文の直後、`[TOC]` の前に `4行まとめ` を入れます。読者が記事全体の価値を10秒で判断できるようにするためです。

4行まとめのルール:

- 見出しは原則 `## 4行まとめ`
- 4つの箇条書きにする
- 1行ごとに、結論、理由、実務での使い方、最初の行動のどれかを入れる
- 長くしない。1項目は40〜70字程度を目安にする
- 本文の要約ではなく、読者が読み進める判断材料にする
- ライト / Pro 記事では、無料部分だけでも価値が伝わるようにしつつ、有料部分の具体手順に自然につなげる

例:

```markdown
## 4行まとめ

- Codexは「賢くなった」というより、作業の文脈を渡しやすくなった
- Appshotsは、画面状態を前提にした依頼をしやすくする機能
- Goal modeは、成果物ベースで長い作業を任せるときに効く
- まずは小さな修正より、調査から実装までの一連の作業で試すとよい
```

## 書き出しで必ず入れる信頼材料

無料公開記事でも、ライト / Pro の有料記事でも、書き出しには「なぜこの記事を読む価値があるのか」が伝わる信頼材料を入れます。

ここでいう信頼材料は、派手な肩書きだけではありません。記事テーマに関係する小さな数字、経験、検証、読者や受講者の変化、調査量、実例も含みます。

書き出し前に、必ず次を探します。

- 自分たちの実績: 運用している講座、コミュニティ、LMS、ハンズオン、記事、検証回数、サポート人数など
- 調査・検証の実績: 読んだ公式資料、比較したツール、試した手順、確認した投稿数、検証した環境など
- 読者や受講者の変化: つまずきが解消した、記事化できた、開発が進んだ、運用が安定したなど
- 数字にできるもの: 回数、人数、期間、記事数、講義数、検証時間、事例数、投稿数など
- 第三者の声: Discord、講義後の反応、相談内容、よくある質問など。個人情報や本人特定につながる情報は出さない

書き出しで使える主要実績:

- 登壇実績: 議員会館での登壇経験
- 登壇実績: 大阪万博での登壇経験
- 開発実績: 大学生というブランディングを活かし、月売上60万円のプロダクトを開発
- 開発実績: 1週間スパンでのアプリローンチ
- 開発実績: AIエージェントの開発
- 開発実績: MCP（Model Context Protocol）の開発
- 開発実績: 独自エージェントの開発
- 開発実績: 週に1回のペースでオープンソースを作成
- マーケティング実績: X（旧Twitter）のフォロワー数 1.8万人
- マーケティング実績: 4ヶ月間でフォロワーを8,000人増加させたマーケティングノウハウ
- コミュニティ実績: 100人規模のコミュニティ運営
- コンサル実績: 僕が1:1でAI活用やAIエージェント開発の相談に乗っている「ガチコンサル」で、AIエージェントやMCPの作成を支援
- 経営者支援: コンサルを通じて経営者と対話し、開発やAI活用を手助けしている
- プロダクト実績: 僕が作っているHTML/CSSからPowerPointを生成するサービス「HTML2PPTX」を開発・運用している

主要実績の使い分け:

- AI開発、Codex、アプリ開発、AIエージェントの記事では、開発実績、MCP開発、独自エージェント開発、オープンソース作成、コンサルでの実装支援を記事ごとに切り替えて使う
- 発信、集客、note、X、コミュニティ、マーケティングの記事では、Xフォロワー数や4ヶ月で8,000人増加の実績を優先する
- コミュニティ、教育、継続学習、Discord、メンバーシップの記事では、100人規模のコミュニティ運営を優先する
- MCP、エージェント、業務自動化、開発支援の記事では、ガチコンサル、MCP開発、独自エージェント開発、経営者支援の実績を優先する
- MCPサービス、Skills、スライド生成、資料作成、HTML変換、業務ツール化の記事では、HTML2PPTXを「自分で作っているサービスの実例」として優先してよい
- 社会実装、教育、行政、イベント、事業性の記事では、議員会館や大阪万博での登壇経験を優先する
- 1記事の冒頭に入れる主要実績は原則1〜2個までにする。全部を並べて自己紹介のようにしない
- 必要なら無料部分の途中に別の実績をもう1つだけ補足する
- 記事テーマに関係しない実績は使わない
- 開発系の記事で毎回同じ実績を繰り返さない。前回使った実績に引っ張られず、記事テーマに最も近い信頼材料を選ぶ
- 開発系の記事では、実績だけでなく「検証したこと」「コンサル現場で見た課題」「コミュニティで多かったつまずき」「公式情報を調べた量」も信頼材料として使ってよい

固有名詞の出し方:

- 固有名詞は「入れる」ことを目的にしない。記事テーマと自然につながる場合だけ使う
- 初出で文脈が伝わらない固有名詞を急に出さない。読者が知らなくても意味が分かる説明を短く添える
- ガチコンサルを出す場合は、初出で「僕が1:1でAI活用やAIエージェント開発の相談に乗っている『ガチコンサル』」のように説明する
- HTML2PPTXを出す場合は、初出で「僕が作っているHTML/CSSからPowerPointを生成するサービス『HTML2PPTX』」のように説明する
- 固有名詞を出した結果、宣伝感が強くなる、本文の流れが止まる、読者に関係が薄くなる場合は、一般化した表現に置き換える
- 例: `ガチコンサルでも` だけで始めない。`僕が1:1でAI活用やAIエージェント開発の相談に乗っている「ガチコンサル」でも` のように、なぜその実例を出すのかが伝わる形にする

書き方の方針:

- 冒頭で1つだけ出すのではなく、タイトル、リード文、無料部分の途中に自然に散りばめる
- 大きな実績がない場合でも、小さな数字や具体的な観察を使う
- 「すごそうに見せる」ためではなく、「この記事の判断材料として信頼できる」と伝えるために使う
- 数字や実績を盛らない。確認できない実績は書かない
- 有料記事では、無料部分に信頼材料を必ず入れる。読者が「この人・このコミュニティの続きなら読みたい」と思える状態を作る
- 無料記事でも同じように、冒頭に記事の根拠や検証量を入れる。無料だからといって単なる一般論から始めない

書き出しの型:

```markdown
<読者が今困っていること。抽象論ではなく、具体例を1〜3個入れる。>
```

無料公開記事では、次を守ります。

- 有料区切りを入れない
- メンバー向け導入文を入れない
- `ここから先はメンバー向け` と書かない
- 記事単体で役に立つ内容を最後まで公開本文に入れる

ライト / Pro 記事では、次を守ります。

- 無料部分は役に立つが、完全な実装手順までは出し切らない
- コマンド、再利用できるプロンプト、セットアップ手順、詳細チェックリスト、失敗パターン、実装メモ、運用上の注意は有料区切りの後に置く
- 無料部分だけで完全に再現できる手順を置かない
- 有料区切りは、読者が「続きを読む価値」を理解した直後に置く。無料部分で本文の大半を見せない
- 有料区切りの直前には、メンバー部分で得られる具体的な内容を短く列挙する

有料区切りの基本形:

```markdown
ここから先はメンバー向けです。<メンバー部分で得られる具体的な価値>.

## ここから先はメンバー向け: 実践テンプレートと運用手順
```

## 図解、スクリーンショット、アイキャッチ

画像の適用方法は、宮田さん向けX記事の編集ビジュアル設計を基準にし、noteの表示仕様へ適応します。共有するのは「画像で比較・因果・流れ・構造を説明する方法」だけです。宮田さん本人の文体、人格、CTA、顧客固有情報、固有の主張は流用しません。

すべての記事に、必ず次を含めます。

- 記事内容を説明する本文ビジュアルを5枚以上。長文記事は10枚を標準にする
- 長文で10個の理解ポイントを抽出できない場合は、装飾画像で埋めず、記事構成を見直す
- そのうち最低1枚は、画像だけで記事の中心内容を理解できる「主解説図」にする
- 主解説図は `imagegen` で生成し、身近なたとえ、実際の構造、成功・失敗、結論を一枚の物語として示す
- 残りは、公式画面のスクリーンショット、実際の検証結果、比較図、手順図、HTML/CSS図解、補助イラストを記事内容に応じて組み合わせる
- HTML/CSS図解を使う場合はラスター画像として書き出す
- 各本文ビジュアルをnoteの本文画像としてアップロードする
- noteにアップロードされたURLを本文へ埋め込む
- 各本文ビジュアルを、それが説明する主張または段落の直後に置く
- noteアイキャッチを必ず作成する
- アイキャッチサイズは正確に 1280:670 にする
- 記事末尾用CTA画像を必ず入れる

CTA画像とアイキャッチは、本文ビジュアルの枚数には数えません。同じ内容を別デザインで繰り返した画像、説明対象がない装飾画像、読めない画面は枚数に数えません。

### 画像ストーリーボードと挿入位置

本文画像を作る前に、`visual-storyboard.md` または同等の記録を作ります。画像ごとに次を記録します。

- 番号
- 挿入する見出し・段落
- 対応する本文の主張
- 読者に理解してほしいこと
- 図解形式
- ファイル名
- note-hosted URL

本文図解は原則16:9とし、1枚につき1つの関係だけを説明します。画像内はビジュアル60〜75%、文字25〜40%を目安にし、ラベルは3〜5個までに抑えます。大きなタイトル、中央の関係図、短い結論の順で構成し、文章をカード化しただけの画像、意味のない3D箱、一般的なAI人物画像は不合格にします。

最初に主解説図を1枚だけ作り、スタイルアンカーとして目視確認します。文字量、配色、線、余白、情報密度が合格してから、残りを同じデザインシステムで作ります。比較、フロー、階層、タイムライン、チェックリストなど、論点に合う形式を使い分けます。

画像はh2の先頭や末尾へ機械的に置きません。対応する主張を本文で述べた直後へ置き、読者が文章と図を往復せず理解できるようにします。

本文ビジュアルの基本セット:

- 主解説図: 問題の全体像、仕組み、成功・失敗、結論
- ワークフロー
- Before / After 比較
- 実践チェックリスト
- リスク・失敗パターン
- 次の行動ロードマップ

本文ビジュアルは飾りではなく、近くの本文を理解しやすくするために使います。note本文幅で読んでも文字が読めるサイズにします。

### 主解説図は「1枚の教材」にする

無料、ライト、Proのすべての記事で、最低1枚の主解説図を必須にします。

- 画像単体を見た人が、記事の中心内容を一文で説明できる状態にする
- 上部に短い日本語タイトル、中央に入力・判断・成功・失敗の因果関係、下部に覚えてほしい一文を置く
- 身近なたとえを使う場合は、料理、空港、鍵と部屋、駅、工場、登山などから記事内容に必然性のあるものを選ぶ
- たとえは説明全体で一貫させ、途中で別の比喩へ切り替えない
- 「何が入力か」「途中で何を判断するか」「成功と失敗がどう分かれるか」「結局どうすべきか」が3秒で追える構図にする
- 日本語は説明に必要な短い語句だけを大きく使い、長文を画像内へ詰め込まない
- 文字化け、誤字、意味不明なラベルが1つでもあれば再生成する
- 抽象的な雰囲気画像、装飾イラスト、単なる工程アイコン、本文を読まないと意味が分からない画像は主解説図として不合格にする

### 絵柄・色・構図の模倣禁止と重複防止

参考画像から利用してよいのは、情報階層、因果関係、視線誘導などの「1枚で理解させる情報設計」だけです。

- 参考画像の絵柄、画材感、色合い、人物配置、吹き出し、札、枠、文字の描き方、画面分割、構図をコピーしない
- 特定の作家、媒体、既存画像と同じ絵柄に寄せない
- 参考画像が手描き・色鉛筆風なら、同じ手描き・色鉛筆風を選ばない
- 参考画像と同じ背景色、主色、アクセント色の組み合わせを使わない
- 「少し色を変えた」「人物だけ変えた」程度では別デザインとみなさない

生成前に、利用可能な直近10記事のアイキャッチと主解説図を確認します。次の4項目のうち最低3項目を、直近の画像から明確に変えます。

1. 表現形式: クリーンなベクター、アイソメトリック3D、紙の切り絵、写真コラージュ、設計図、ミニチュア模型、雑誌インフォグラフィックなど
2. 配色: 背景色、主色、アクセント色
3. 構図: 横移動、中央集約、上下比較、円環、俯瞰、断面図など
4. 比喩・舞台

同じ表現形式と配色を連続使用しません。記事の内容から `visual_direction`、`palette`、`metaphor` を先に決め、`source-notes.md` またはhandoffへ記録します。

主解説図のQAでは、次を記録します。

- `teaching_infographic_present`
- `teaching_infographic_message`
- `metaphor`
- `input_decision_result_flow`
- `three_second_comprehension_passed`
- `visual_direction`
- `palette`
- `recent_visuals_checked`
- `visual_difference_summary`

`three_second_comprehension_passed=false`、文字崩れ、参考画像との近似、または直近画像との差が説明できない場合は再生成します。

スクリーンショットの方針:

- 顔中心の画面より、関連するUIや画面共有を優先する
- Zoom参加者一覧、Webカメラの顔、無関係な黒帯、読めないUIは切り取る
- 近くの文章を直接支えないスクリーンショットは、図解に置き換えるか削除する

アイキャッチの方針:

- サイズは必ず 1280:670
- 左55〜60%に短い大見出し、補足1行、必要最小限のタグを置く
- 右40〜45%に、記事の中心となる仕組み、比較、流れを示す大きな主役モチーフを置く
- 右側を無意味な余白、薄い模様、装飾だけで終わらせない
- noteフィードの小さい表示でも、見出しと右側モチーフの両方が識別できることを確認する
- アイキャッチの主画像は必ず Image 2 / `imagegen` で生成する。HTML/CSSだけで作った画像を最終アイキャッチにしてはいけない
- Image 2 / `imagegen` の生成画像が正確に 1280:670 でない場合は、比率を崩さずトリミングまたはリサイズして 1280:670 に整える
- HTML/CSSは、生成画像の文字入れ補正、レイアウト調整、図解作成には使ってよいが、アイキャッチのベース画像は必ず Image 2 / `imagegen` を使う
- 日本語タイトル、バッジ、note向けラベルを重ねる場合はHTML/CSSで読みやすく整える
- noteフィード上で読めるように、高コントラスト、明確な主題、短いタイトルにする
- 薄いだけの背景、細かすぎるUI、荒い日本語文字、情報過多の見た目を避ける
- バッジ文言は子スキルの設定に従う

アイキャッチQAフィードバックループ:

1. アイキャッチ作成時は、まず `imagegen` スキルを使用して主画像になるラスター画像を生成する。
2. HTML/CSS、SVG、canvas、Playwright/Puppeteerスクリーンショット、`render-assets.mjs` などで最初から作った画像を、最終アイキャッチの主画像として使ってはいけない。
3. HTML/CSSを使ってよいのは、`imagegen` で生成した主画像に対する文字入れ、外枠、バッジ、特典チップ、軽いレイアウト補正、1280:670への整形だけ。
4. 最終アイキャッチの元になった `imagegen` 出力パス、最終アイキャッチパス、使用プロンプトをローカルの結果メモまたはhandoffに残す。
5. 最終アイキャッチを保存したら、公開前に必ず目視確認する。確認項目は、1280:670、タイトル可読性、バッジ文言、AI PLAY GUILDラベル、ツール色、特典チップの正当性、文字崩れ、情報過多、noteフィードでの視認性。
   さらに、右40〜45%の主役モチーフが存在し、記事内容を説明し、小さい表示でも認識できることを確認する。右側が空白または装飾だけなら不合格にする。
6. 目視確認で、HTML/CSSだけで作った図解のように見える、`imagegen` 由来の主画像が確認できない、または生成画像ではなく単なるHTMLカード画像になっている場合は不合格にする。
7. 不合格の場合は、`imagegen` で主画像を再生成し、同じQAを再実行する。HTML/CSS側だけを調整して合格扱いにしてはいけない。
8. 公開前チェックでは、`eyecatch_source=imagegen`、`imagegen_output_path`、`final_eyecatch_path`、`eyecatch_qa_passed=true` 相当の証跡を確認する。
9. `python3 <skill-dir>/scripts/validate_eyecatch.py <final_eyecatch_path> --json-output <qa-dir>/eyecatch-lint.json` を実行し、終了コード0を必須にする。
10. 機械検査の後、別の確認パスとして最終画像を `view_image` で開き、外枠、ブランドラベル、タイトル、サブタイトル、トピックタグチップを目視する。作成直後の印象だけで合格にしてはいけない。

AI Play Guild アイキャッチ共通デザイン:

- 画像の四辺すべてに14〜20pxの太い外枠線を必ず入れる。色は黒固定ではなく、記事テーマ、主画像、アクセントカラーに合う色を選ぶ
- 外枠は四辺で連続し、内側のデザインと視覚的に分離している必要がある。背景と同化して枠に見えない場合は不合格にする
- 外枠色を選んだ理由を `frame_color_rationale` としてQA記録へ残す
  - Codex / OpenAI系: 深いグリーン、黒、白を基調にする
  - Claude / Anthropic系: 温かいオレンジ、生成り、黒を基調にする
  - Google / Gemini系: 青、赤、黄、緑のうち1〜2色をアクセントにする
  - GitHub / 開発基盤系: 黒、白、グレー、紫寄りのアクセントを使う
  - X / SNS系: 黒、白、ブルーを基調にする
  - note / 発信系: グリーン、白、黒を基調にする
- 枠線は単なる装飾ではなく、noteフィード上でAI Play Guildの記事だと判別できる共通記号として扱う
- 左上に小さく `AI PLAY GUILD` のラベルを入れる
- ラベルはロゴ風にしすぎず、細い枠、短い帯、または小さなタグとして置く
- `APG`、`FIELD NOTES` など、意味が伝わりにくい略称や雰囲気ラベルは使わない
- 記事内で特定ツールが明示されている場合は、そのツールのアイコンまたはアイコン風の識別記号を入れる
  - 公式ロゴを使える素材として持っている場合は、歪ませず、小さめに配置する
  - 公式ロゴ素材がない場合は、ロゴを模倣せず、色と簡潔な記号で「そのツールらしさ」を表現する
  - ツールアイコンは主役にしすぎず、タイトルの補助として右上、左下、または背景UI内に置く
- 右下には、記事に明確な配布物や特典がある場合だけ、目に留まる小さな特典チップを置く
  - 例: `Skills配布`, `プロンプト配布`, `テンプレ配布`, `チェックリスト付き`, `実装手順付き`
  - 実際に本文内で提供しない特典は書かない
  - 特典チップは1つ、多くても2つまでにする
- メインタイトルは中央またはやや左寄せに大きく置き、短い日本語にする
- サブタイトルは1行だけにし、ツール名、論点、対象者を短く並べる
- サブタイトルの下または左下に、記事内容を表すトピックタグチップを2〜4個置く
  - 例: `Codex`, `Claude Code`, `Local AI`
  - 本文で実際に扱う短い固有名詞または論点だけを使う
  - プランバッジや特典チップはトピックタグ数へ含めない
- 背景には、その記事のツールやテーマを連想できるUI、抽象的なワークフロー、カード、コード、エージェント、図形を置く
- 背景は暗くしすぎず、タイトル周辺には読みやすい余白または半透明の面を作る
- 参考画像のような「太い枠線 + 中央タイトル + 小さなコミュニティラベル」の読みやすさは取り入れてよい
- ただし、特定メディアや他コミュニティのロゴ配置、色面、文字組み、写真構図をそのままコピーしない
- 量産型のAI画像に見えないように、記事ごとにテーマツールの色、モチーフ、レイアウトの重心を変える

```text
中央またはやや左に、短い日本語タイトルを大きく配置する。サブタイトルは1行だけ。
サブタイトルの下または左下に、本文で実際に扱うトピックタグチップを2〜4個配置する。プランバッジや特典チップとは別にする。
背景には、記事テーマを連想させるUIカード、コード断片、ワークフロー、AIエージェント、抽象的なツール画面を配置する。
noteのフィードで小さく表示されても、タイトルとテーマが一瞬で分かる構図にする。
過度なグラデーション、暗すぎるサイバー感、読めない細かい文字、他メディアのロゴや構図の模倣、情報過多を避ける。
```

## リンク参照と埋め込み

記事内にリンクを入れる場合、埋め込み可能なURLは原則すべて埋め込みカードにします。これは本文中の参考リンク、公式資料、X投稿、YouTube、GitHub、note記事、`## あわせて読みたい` のおすすめ記事すべてに適用します。

基本方針:

- 埋め込み可能なURLは、通常のMarkdownリンクではなく、URL単独行で置く
- URLの前後には空行を入れ、note-mcpが1つの独立した段落として扱えるようにする
- 箇条書きの中にURLを置かない。`- https://...` は埋め込みにならないため避ける
- `[表示テキスト](URL)` は、埋め込み非対応URL、文中引用を優先したい場合、またはプレビューで埋め込み失敗が確認された場合だけ使う
- 埋め込み可能か迷ったURLは、まず単独行で入れてプレビューを確認する
- プレビューでカード化されなかったURLだけ通常リンクに戻す

note-mcpで埋め込み変換に対応している主なURL:

- note記事URL: `https://note.com/<user>/n/<article_key>`
- X / Twitter投稿URL
- YouTube / youtu.be
- GitHubリポジトリURL
- GitHub Gist URL
- Google Slides
- SpeakerDeck
- Zenn記事
- Qiita記事
- connpassイベント
- money.note.com

埋め込みの書き方:

```markdown
参考になる公式発表はこちらです。

https://example.com/embeddable-url

この内容を踏まえると、実務では次の観点が重要です。
```

禁止例:

```markdown
- https://note.com/<user>/n/<article_key>

[参考記事はこちら](https://note.com/<user>/n/<article_key>)
```

上の2つは、カード化したいURLでは使いません。埋め込みたい場合は必ずURLだけを1行で置きます。

埋め込み後の確認:

- プレビューHTMLで、意図したURLが `<figure>` または `embedded-service` 付きの埋め込み要素になっていることを確認する
- 埋め込み予定のURLが、ただの文字列、通常の `<a>`、箇条書きリンクのまま残っていないか確認する
- 対応URLなのに埋め込まれていない場合は、URLを単独行に直して再保存する

## note API 共通ワークフロー

note操作には `note-mcp` を使います。noteツールが使えない場合、投稿できたふりをしてはいけません。ローカルのMarkdownと画像まで準備し、note書き込み前で止めます。

想定するグローバルMCP設定:

```toml
[mcp_servers.note-mcp]
command = "uv"
args = ["run", "--directory", "<path-to-note-mcp>", "python", "-m", "note_mcp"]
```

主に使うツール:

- `note_check_auth`
- 必要な場合だけ `note_login`
- プラン限定公開の前に `note_list_circle_plans`
- `note_create_draft` または `note_update_article`
- `note_upload_eyecatch`
- `note_get_preview_url`
- 必要に応じて `note_get_preview_html`
- 有料記事では `note_get_separator_candidates` と `note_set_paid_settings`
- 明示的な公開許可がある場合だけ `note_publish_article`

下書きルール:

- 記事キーを必ず保持する。例: `nc19f084da421`
- 編集URLはキー形式を使う: `https://editor.note.com/notes/<article_key>/edit/`
- 数値IDの編集URLに依存しない。本文が存在しても `0文字` と表示されることがある
- プレビューURLは確認用であり、プレビューから公開するわけではない
- 本文更新後は、可能な限りプレビューHTMLまたは生のarticleデータで本文が入っていることを確認する

## 公開前ダブルチェック（Hard gate）

下書き保存後は、画像だけでなく記事全体を2つの異なる方法で検査します。本文、箇条書き、番号、コマンド、リンク、画像、目次、有料区切り、アイキャッチのすべてが対象です。APIが成功した、本文長が0ではない、HTTP 200だった、という確認だけでは公開してはいけません。

本文でコマンド例やプレースホルダーを書くときは、 `` `/prototype <説明>` `` のように山括弧をinline codeへ入れません。note変換でHTMLタグとして欠落する可能性があるため、 `` `/prototype ［説明］` `` のような全角角括弧を使います。

### Pass A: 変換後HTMLの機械検査

1. 最終更新後のnote実プレビューHTMLをファイルへ保存する。
2. 次を実行する。

```bash
python3 <skill-dir>/scripts/validate_note_preview.py \
  --source <article.md> \
  --preview-html <preview.html> \
  --min-images 6 \
  --min-h2 2 \
  --require-toc \
  --json-output <qa-dir>/preview-lint.json
```

3. 空の `li`、句読点から始まる孤立段落、inline code欠落、`<pre>` 外の `<code>`、生Markdown、プレースホルダー、画像不足、見出し不足、目次欠落のどれかがあれば不合格にする。
4. Markdown内のすべてのinline code文字列が、変換後の可視テキストへ残っていることを確認する。
5. ストーリーボードの全画像にnote-hosted URLがあり、予定枚数とプレビューHTMLの本文画像数が一致することを確認する。ローカルパスや未置換の `<!-- IMAGE:` が残っていれば不合格にする。

### Pass B: 実プレビューとアイキャッチの目視検査

1. noteの実プレビューURLをブラウザで開き、本文をスクリーンショットにする。HTML文字列だけを見て完了にしない。
2. 元Markdownを横に置き、箇条書き、番号、inline code、コマンド、画像、目次、有料区切りを上から順に照合する。
3. 空の点だけの箇条書き、大きすぎる空白、「：説明」だけの行、欠けたコマンド、画像の連続失敗が一つでもあれば不合格にする。
4. 最終アイキャッチを別に開き、デザインに合う四辺の太い外枠、枠と内側の視覚的分離、`AI PLAY GUILD`、主見出し、1行サブタイトル、2〜4個のトピックタグチップを確認する。
5. Pass Aを実行した確認とPass Bを実行した確認を別工程として記録する。同じ画面を一度見ただけで「ダブルチェック済み」としてはいけない。

### Pass C: 文章・構成・事実の独立レビュー

執筆工程とは別のChecker工程として、完成した実プレビューを最初から読み直します。書いた意図を補って読まず、初見の読者として判断します。

編集レビューでは、次を確認します。

- タイトル、アイキャッチ、リード、4行まとめ、本文の結論が同じ約束をしている
- 主語と述語、助詞、時制、固有名詞、句読点が自然で、誤字や音声入力由来の崩れがない
- 同じ説明の重複、急な話題転換、説明不足、過剰な断定、AIが生成したような空疎な一般論がない
- 箇条書きが単なる羅列ではなく、分類と順序に意味がある
- 初出の専門用語に説明があり、読者が次に何をすればよいか分かる
- 無料部分と有料部分の境界が自然で、有料部分の価値を誇張していない
- 記事末尾が本文の内容から自然につながり、不要な売り込みになっていない

事実レビューでは、`source-notes.md` と一次情報を横に置き、次を一つずつ照合します。

- 製品名、人物名、会社名、日付、数値、価格、プラン、提供状況
- コマンド、URL、リポジトリ名、API名、機能名、制限事項
- 公式情報、X上の発言、書き手の推測・提案が明確に分かれている
- 一次情報で確認できない断定に、推定であることの表示または削除がある
- 出典リンクが本文の主張を実際に支えている

問題を見つけたら、`unresolved_editorial_findings` または `unresolved_fact_check_findings` に記録してから修正します。未解決項目が一つでもある間は公開してはいけません。修正した場合は、Pass A、Pass B、Pass Cをすべてやり直します。

`qa-gate.json` または同等の記録へ、少なくとも次を残します。

- `preview_lint_passed`
- `visual_preview_passed`
- `eyecatch_lint_passed`
- `eyecatch_visual_passed`
- `editorial_review_passed`
- `fact_check_passed`
- `editorial_review_summary`
- `fact_check_summary`
- `unresolved_editorial_findings`
- `unresolved_fact_check_findings`
- `topic_chips`
- `frame_color_rationale`
- `checked_after_last_update`
- `source_sha256`
- `source_notes_sha256`
- `preview_html_sha256`
- `eyecatch_sha256`

Pass A、Pass B、Pass Cの完了後、次を実行します。

```bash
python3 <skill-dir>/scripts/validate_qa_gate.py \
  --gate <qa-dir>/qa-gate.json \
  --source <article.md> \
  --source-notes <source-notes.md> \
  --preview-html <preview.html> \
  --eyecatch <final_eyecatch_path>
```

終了コード0の場合だけ公開できます。本文、ソースメモ、実プレビューHTML、アイキャッチのSHA-256が記録と違う場合は、以前の合格を無効にします。修正後にPass A、Pass B、Pass Cをすべてやり直します。

有料設定:

- ライト / Pro では、最終本文更新後に有料区切りを入れる
- 本文更新のたびに区切り要素のUUIDが変わる可能性がある
- `note_update_article` の後は毎回 separator candidate を取り直し、現在のUUIDに対して有料設定を適用する
- 無料記事では、有料区切り、`limited=True`、circle plan、価格が入っていないことを確認する

## 目次の扱い

記事が短すぎる場合を除き、リード文の後に `[TOC]` を入れます。

note.com では、目次について次の挙動があります。

- 編集画面では目次ブロックが見えていても、公開ページでは初回に目次が出ない場合がある
- API直公開では、本文内に `<table-of-contents>` が保存されていても、公開ページ用の `index` データが生成されないことがある
- 編集画面から手動保存・公開すると、その `index` データが再生成されることがある

そのため、目次ありの記事では必ず追加確認をします。

1. 公開前に、下書き本文に目次ブロックと複数の `h2` 見出しがあることを確認する
2. 公開後に、公開ページで目次が表示されていること、または note API の `data.index` に見出し一覧が入っていることを確認する
3. 公開ページの目次がなく、`data.index` も空の場合は、作業完了扱いにしない
4. その場合は、編集画面・ブラウザ経由で保存または公開フローを通し直し、再確認する
5. HTTP 200、タイトル表示、編集画面の目次表示だけでは、目次確認を完了扱いにしない

目次を短く保つため、本文作成後に `##` と `###` の数を確認します。目次項目が10個を超える場合は、章として飛ばす必要がない見出しを太字テキストに変更します。読者が目次から移動したいのは大きな章であり、細かい項目ではありません。

ブラウザや編集画面の自動操作が使えず、公開ページ上の目次を確認できない場合は、そのことを明確に報告します。

## 公開手順

`公開して`、`投稿して`、`Discordに送って` のような新しい明示指示がない限り、公開してはいけません。

公開が許可された場合の手順:

1. 最終本文更新、ビジュアルプレビュー確認、アイキャッチアップロード、本文画像アップロード、有料設定を完了する
2. 有料記事では、最後の本文更新後に現在のseparator UUIDを取り直す
3. 目次ありの記事では、公開前に目次・公開用indexの準備状態をできる範囲で確認する
4. 子スキルで決まった公開設定に従って、元記事を公開する
5. 公開URLを作る: `https://note.com/<username>/n/<article_key>`
   - 可能なら認証済みnoteユーザー名を使う
   - 既知のAI PLAY GUILDアカウントでは `meru2002` を使ってよい
6. 公開URLがHTTP 200を返し、記事タイトルを含むことを確認する
7. 目次ありの記事では、公開ページの目次表示または `data.index` を確認する
8. 最終本文から、2つ目の未公開複製下書きを作る
9. 複製下書きにも同じアイキャッチをアップロードまたはコピーする
10. 複製下書きのプレビューURLを取得する
11. Discord配信が依頼または設定されている場合、複製下書きのプレビューURLを主リンクとして送る。公開URLは補足として添える

公開後の複製プレビューは、3つの子スキルすべてで必須です。Discordには、元記事の公開URLをプライマリのプレビューリンクとして送ってはいけません。

## Discordへの複製プレビュー配信

まず `NOTE_PREVIEW_DISCORD_WEBHOOK_URL` を使います。場所はシェル環境変数、または `<project>/.env.local` です。

Webhookがない場合は、`DISCORD_BOT_TOKEN` とチャンネル `1505176930046185632` を使います。別の送信先を勝手に作ってはいけません。

WebhookがDiscordのフォーラムまたはメディアチャンネル用であれば、`thread_name` を含めます。ユーザーが指定していなければ、noteタイトルをスレッド名にします。

すべてのDiscord payloadには `allowed_mentions: {"parse": []}` を入れます。HTTP 204 は成功として扱います。

無料・ライト・Proの3つの記事は、場当たり的にWebhookへ送らず、共通の `/Users/kimurataiyou/.agents/skills/note-light-publish/scripts/deliver_note_preview.py` を使います。子Skillに合わせて `--access-model free`、`light`、`pro` のいずれかを必ず指定します。最初は `--send` なしのdry-runで検証し、現在のユーザーターンで公開・配信が明示承認されている場合だけ `--approved --send` を付けます。このCLIは、公開記事とは別の複製下書きか、主リンクがプレビューURLか、mentionが無効かを検証し、同じ複製の二重送信を防止します。フォーラム・メディアチャンネルでは既定の `thread_name` を使い、通常テキストチャンネルの場合だけ `--no-thread-name` を指定します。

予定実行ではこのCLIのdry-runまでに留め、`--approved --send` を付けてはいけません。公開・複製作成・Discord実送信は、人間の新しい明示承認を受けた継続ターンで一続きに実行します。

状態ラベル:

- 無料: `無料公開 / 公開済み`
- ライト: `ライトプラン限定 / 単発500円 / 公開済み`
- Pro: `Proプラン限定 / 単発2000円 / 公開済み`

ユーザーが明示的に求めない限り、完全な非公開プレビューURL、preview access token、Webhook URL、note cookie、bot tokenを、引き継ぎファイル、設定メモ、git commit、最終回答に書いてはいけません。

## 完了前チェックリスト

完了前に、次を確認します。

- アイキャッチのアップロードにエラーがない
- アイキャッチが正確に 1280:670
- アイキャッチの四辺に14〜20pxのデザインに合う外枠があり、四辺で連続し、内側と視覚的に分離し、機械検査と目視検査の両方に合格している
- 外枠色の選定理由が `frame_color_rationale` に記録されている
- アイキャッチに `AI PLAY GUILD`、1行サブタイトル、本文に対応する2〜4個のトピックタグチップがある
- 冒頭が広すぎる一般論ではなく、読者の具体的な困りごとから始まっている
- リード文の直後、`[TOC]` の前に `## 4行まとめ` がある
- `4行まとめ` が4つの箇条書きで、結論、重要性、実務での使い方、最初の行動を短く伝えている
- 公式情報や一次情報と、自分たちの検証・現場視点がセットで入っている
- 記事テーマに関係する `02-company_knowledge/` と `05-raw-data/` を必要最小限で検索し、使わない場合も理由が `source-notes.md` に記録されている
- ローカルナレッジを使った場合、公開本文へ過去note名やローカルパスを不要に出さず、内部のresource ID・パス・用途だけが `source-notes.md` に残っている
- 第三者由来の固有表現・体験・フレームワークを本人の発案として書いていない
- 機能や論点がカテゴリ分けされ、ただの羅列になっていない
- 最後が一般論ではなく、自分の現場でどう使えるか、次に何を試すかで締まっている
- 本文ビジュアルが5枚以上あり、そのうち最低1枚が「1枚の教材」として成立する主解説図である
- 長文記事では本文ビジュアルが10枚を標準として設計され、減らした場合は記事の理解ポイント数に基づく理由が記録されている
- 画像ストーリーボードに、各画像の挿入位置、対応する主張、理解目標、図解形式、ファイル名、note-hosted URLが記録されている
- 本文図解が原則16:9で、対応する主張の直後に置かれ、1枚で1つの比較・因果・流れ・構造を説明している
- 主解説図の比喩、入力→判断→結果、3秒確認、絵柄・配色・構図の直近記事との差がQAへ記録されている
- 参考画像の絵柄・色合い・構図を模倣しておらず、同じ表現形式と配色を連続使用していない
- 本文ビジュアルがnote-hosted URLとして本文に埋め込まれている
- ストーリーボードの予定枚数・順序・位置と、実プレビューに表示された画像が一致している
