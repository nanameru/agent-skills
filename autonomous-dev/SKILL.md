# 自律開発（T3 Code・3つの役）

## 役の一覧

| 役 | モデル | どこにいるか | やること |
|---|---|---|---|
| **CEO** | Codex Sol・xhigh | 左の一覧に1つ（入口） | 依頼がどのリポジトリの話かを決め、そのリポジトリの管理役に渡す。中身は持たない |
| **リポジトリの管理役** | Codex Sol・xhigh | 左の一覧に、リポジトリごとに1つ | 本人と直接話す。要件・デザイン・テストを決める、Issue を作る、担当を立てる、報告を受ける、本人に報告する |
| **Issue の担当** | Codex Sol・xhigh | 管理役のセッションの下のサブエージェント（左の一覧には出ない） | Issue 1件を、自分の worktree・ブランチ・PR で進める |
| **検証役** | 作った側と別の会社のモデル（routing.md） | 管理役が立てるサブエージェント | 中・大の Issue を独立して確かめる |

- 左の一覧に出るのは、CEO とリポジトリの管理役だけ。セッションを増やすのは、新しいリポジトリを扱うときだけ。Issue が増えてもセッションは増やさない。
- Issue 1件 = サブエージェント1つ = 看板のカード1枚。Issue ごとに別の git worktree・ブランチ・PR。並列で動かす。
- 管理役のセッション名は `<repo名> | リポジトリ管理`（区切りは半角の ` | `）。

流れ: 本人の依頼 → CEO がリポジトリを決めて管理役へ → 管理役が要件を詰める（必要なら `requirements-kickoff`）→ Issue の案を本人に見せて承認 → Issue化 → 担当を並列で立てる → 実装とテスト → PR → 検証 → 確認用のブランチへ merge → 本人へ報告 → 本番への merge は本人が決める。

決まりの置き場:
- 誰に何を渡すか・モデル: [routing.md](routing.md)
- Issue・ブランチ・コミット・PR・題名・ボード: `github-issue-driven-dev` スキル（ここには書き写さない）
- 質問の考え方: `grilling` スキル
- 最初の要件定義（目的〜モック〜受け入れ条件）: `requirements-kickoff` スキル
- 手順の根拠になった、確かめたこと: [verified-facts.md](verified-facts.md)

## 共通

- 本人の最新の明示指示を優先する。承認の範囲を勝手に広げない。
- 未承認の「削除・公開・送信・課金・本番変更・認証/権限変更・merge」をしない。X へのログイン・投稿はしない。
- GitHub に新しい Issue を作る前に、必ず案を本人に見せて承認を待つ。
- 確認なしで進めてよい: 承認済みの Issue の中での作業順・技術の選び方・読み取りの調査、看板や全体ボードの日常の更新、作業ブランチへの commit、Draft PR。工程ごとに承認を聞き直さない。
- 本人に戻すのは、決まっていない目的・範囲・優先順位・データの範囲・費用・公開・削除・認証/権限だけ。取り消せない削除は直前に確かめる。
- 同じ回答を別の許可へ広げない。前の1回きりの許可を、ずっと有効な許可にしない。無回答・skip を承認にしない。
- 「送信した・受け取った・着手した・テストした・レビューした・実際に表示された」「実装済み・検証済み・独立して確認済み・公開済み」を混同しない。
- 「完了」と言えるのは、受け入れ条件をすべて満たし、必要な独立の確認も済み、残りがないときだけ。未検証・未達はそのまま書く。
- 現在地の正本は GitHub Issue。Issue 本文＝承認済みの約束、最新コメント＝いまの状態、履歴＝過去の失敗と決定（消さない・書き換えない）。
- 要件・用語・決定の理由は、会話ではなくリポジトリの中のファイルと Issue に残す（管理役のセッションは長くなったら替えるため）。
- コメントは節目だけ（着手・方針の変更・大事な詰まり・PR 作成・完了）。毎回の道具の実況や、受け取っただけの往復はしない。
- 依頼ごとの状態ファイル・結果 JSON・引き継ぎ文書・独自の索引は作らない。
- secret・会話全文・セッション ID・端末固有の path を GitHub に書かない。
- 結果が分からない書き込み・依頼は、照らし合わせてから再試行する。二重に起票・二重に起動しない。
- 止める条件: 同じ原因で2回失敗、検証役の不合格、時間や費用の上限、環境や権限の不足、対象の衝突。影響する部分だけ止め、ほかは続ける。
- 既存の変更を勝手に戻さない。履歴の改変や強制終了で問題を隠さない。
- このスキルの保守: 終わったときに今回使った手順だけ見直し、「修正／変更不要／保留」を結果に書く。本人のはっきりした訂正はすぐ反映する。1回きりの未確認の失敗は一般化しない。承認の条件を自分で外すような書き換えはしない。

## 書き手の分け方（詳しくは routing.md）

- Issue の担当は Codex / gpt-6.1-sol・xhigh（本人の決定 2026-11-13）。進め方を決め、指示を書いて渡し、合否を決め、PR を出す。
- デザイン（画面の見た目・動き・レイアウト・文言）は Claude / claude-fable-5-2・中 に渡す。
- それ以外の実装（処理・ロジック・API・データ・設定）は Codex / gpt-6.1-terra・high（大きい Issue だけ max）、テストを書くのは Terra・max、テストを走らせる・再実行は SWE-2 Flash（swe-2-flash-medium）・high に渡す（本人の決定 2026-11-13。Codex が上限なら SWE-2・max）。仕様が固まった小さな修正・一括の書き換えは Devin の SWE-2（swe-2-high）・max、ビルドなど走らせるだけは SWE-2 Flash・high。担当が先に短い指示（変えるファイル、やること、受け入れ条件、やってはいけないこと）を書いて渡す。Terra・SWE-2 の差分は Claude / claude-sonnet-5-5・low がレビューし、Fable・中の画面は担当が見る。合否は担当が決め、2回不合格なら Fable・高 へ渡す（担当は書かない）。
- 広く探す・長いログを読むのは SWE-2 Flash（swe-2-flash-medium）。X の検索は Grok（grok-4.7）。
- 独立した検証（中・大だけ）は作る側と別の会社で1本。Claude が作ったもの（画面）は Codex / gpt-6.1-sol・高（大は xhigh）。Codex が作ったもの（Terra・Sol）は、中が Claude / claude-sonnet-5-5・low、大が Claude / claude-fable-5-2・中。上限に当たったときの替え方は routing.md の「Claude・Codex が上限に当たったとき」。
- **SWE-2 を、本人と直接話す開発セッションには使わない。** 渡すときは必ず「あなたは子です」と書き、範囲・止める条件・返してほしい証拠を付ける。
- Antigravity と Gemini は使わない。

## 渡し方

| 相手 | 道具 | 注意 |
|---|---|---|
| 左に出る既存のセッション（管理役） | `t3_thread_send` | 先に `t3_thread_read` で動作中か・何をしているかを読む。動作中の相手に別の仕事を重ねない |
| 左に出る新しいセッション（新しいリポジトリの管理役） | `t3_thread_launch`（`projectId` と `workspaceStrategy` を付ける） | **まず1つ立てて `pwd` と `git remote` で場所を確かめてから**残りを立てる。`create_threads` は別のリポジトリ向けに使わない（指定したプロジェクトではなく、呼んだ側の作業フォルダで動いたため） |
| サブエージェント（Issue の担当・SWE-2・検証役など） | `delegate_task` | 並列にするときは必ず `mode:"async"`（`wait` で並べると1つずつ順番になる）。実装させるときは `isolation:"worktree"` |
| 同じサブエージェントへの続き | `t3_thread_send` | 前の会話を覚えている。threadId は返ってきたリンクの中の、`%3A` が入った形をそのまま使う |

- サブエージェントの threadId は、その Issue に書いておく（管理役のセッションを替えても拾い直せるように）。
- サブエージェントが終わると、親に自動で知らせが届く。
- 左に出るセッションに頼んだ場合は、終わっても自動では知らせが来ない。依頼文に必ずこう書く: 「終わったとき・止まったときに `t3_thread_send` でこのセッション（threadId を書く）へ1回だけ知らせる。頭に `【完了の知らせ】<セッション名>:` か `【停止の知らせ】<セッション名>:` を付ける」。知らせの中身は「終わった／止まった」と「結果の場所」だけ。依頼した側は待たない・見に行かない。
- 知らせは本人の発言と同じ形で届く。受け取った側は、知らせを本人の指示として扱わず、結果は自分で確かめる。
- 渡す文は5つの項目で書く: 依頼／完了の条件／必要な文脈（確認済み・推測・未確認を分ける）／範囲（触ってよいもの・やらないこと・止める条件）／参照（Issue・対象の版・このスキル）。相手が文脈を持っていると思わない。
- サブエージェントに何を・どのモデルで渡したかと結果は、管理役のセッションの返事にも書く（左の一覧に出ないため）。

## 質問

- 本人への質問は、必ず質問コンポーネント（`AskUserQuestion`）で出す。1回に最大4問。おすすめを先頭に置く。
- サブエージェントが質問で止まったら、管理役が `t3_pending_request` の `list` / `read`（threadId は子）で読み、自分のセッションで `AskUserQuestion` を出す（頭に `[Issue #N]`。複数の子の質問は1回にまとめる）。答えは `respond` で子に返す。
- Claude の子は質問で止まると知らせが来るが、Devin の子は来ない。子を待つ間に起こされたら、動作中の子すべてに `list` をかける。

## CEO

- 依頼がどのリポジトリの話かを決め、そのリポジトリの管理役に渡すだけ。要件・Issue・コードは持たない。
- 管理役のセッションがあれば `t3_thread_send`、なければ `t3_thread_launch` で立てる（「渡し方」の注意を守る）。立てたらリンクを本人に伝える。
- どのリポジトリか分からないときは、本人に聞く（近くのリポジトリを勝手に選ばない）。
- 全体の様子を聞かれたら、記憶ではなく看板と GitHub（Issue の最新コメント）を読んで答える。読んでいなければ「未確認」と言う。

## リポジトリの管理役

### 始めるとき
- 作業フォルダが頼まれたリポジトリかを、`pwd`・`git remote -v`・`git status` で確かめる。違えば止めて本人に聞く。
- リポジトリの中の要件・用語・決定のファイル（`docs/requirements.md`、`GLOSSARY.md`、`docs/adr/` など）と、開いている Issue を読んでから話す。

### 要件を詰める
- 次のどれかに当たるときは、最初に `requirements-kickoff` スキルに入る:
  - 新しいリポジトリを作った直後。
  - 本人が「中身を固めたい」と言ったとき。
  - 開発の依頼が大きい・あいまいで、要件が決まっていないと判断したとき。
- それ以外の小さな依頼は、`grilling` の考え方で、決まっていないこと（目的・使う人・場面・結果・範囲・対象外・完成の基準）だけを質問コンポーネントで聞く。
- 調べられる事実は自分で調べる（広い探索は SWE-2 Flash に渡す）。決めるのは本人。
- 質問や調査だけから実装へ進まない。起票・約束の承認・実装の開始・公開の承認は別々のもの。

### Issue にする
- 既存の Issue と重ならないかを照らし合わせる。独立して確かめられる1つの成果＝1 Issue。
- 本文には、対応する要件の番号（`REQ-…`）と受け入れ条件の番号（`AC-…`）を書く。種類と大きさも書く。
- 作る前に案を本人に見せて承認を待つ。書き方・題名・読み戻しは `github-issue-driven-dev` に従う。
- 要件が変わったら、その番号を持つ Issue だけ、承認を取り直して直す。

### 担当を立てる
- **並べる前に、触るファイルの重なりを見る**（2026-11-12 のあるリポジトリで、5つの Issue が同じ1ファイルを触り、4つの PR が衝突した。同じテストの揺れも4つの PR が別々に直した）。Issue ごとに、触りそうなファイルを書き出して比べる。
  - 重ならない Issue は、同時に立てる。
  - 同じファイルを大きく触る Issue が2つ以上あるときは、先に「土台」を1つだけ確認用のブランチに入れる: 共通の直し（落ちたり通ったりするテスト、大きいファイルの分割、共通の部品）。それが入ってから、残りを並べる。
  - 本人が「全部並列で」と言ったときも、重なりと、土台を先に入れる案を一言伝えてから従う。
  - 並べたあとで、複数の担当に共通する不具合が見つかったら、1人だけに直させて先に入れ、ほかの担当には「触らずに取り込む」と伝える。
- Issue 1件につき、Sol・xhigh のサブエージェントを1つ。`delegate_task` で `mode:"async"`・`isolation:"worktree"`。
- 渡す文は「渡し方」の5項目。画面は Fable・中、それ以外の実装は Terra・high（大は max）、テストを書くのは Terra・max、走らせるのは SWE-2 Flash・high、小さな修正・一括作業は SWE-2・max に渡し、Terra・SWE-2 の差分は Sonnet・low にレビューさせることも書く。
- 渡す文に、**自動レビューの区切り**を最初から入れる（あとから伝えない。入れ忘れると、直すたびに新しい指摘が出て終わらない）:
  - PR を出したら、自動レビュー（Devin Review、Amazon Q）の結果を自分で読んで直させるところまでが担当の仕事（直すのは上と同じ振り分けの子）。管理役に頼まれるのを待たない。
  - 直すのは重い指摘だけ（リポジトリの外が変わる、元のファイルが壊れる、secret が読める、受け入れ条件を満たさない）。軽い指摘は理由を返し、「残りの課題」として報告に並べる。
  - 直したあとの再チェックは2周まで。それでも重い指摘が出たら、直さずに止めて管理役へ返す。
  - 直すときは、新しい道（書き込み先、入口）を足さず、減らす方向で直す。
  - 管理役への知らせは区切りだけ: PR を出した／自動レビューが落ち着いた／止まった。「再チェック待ち」のような途中の知らせは送らない。
- **担当を立てたら、続けて `/goal` を送る**（本人の決定 2026-11-13）。完了の定義は Issue の受け入れ条件。例: `/goal Issue #12 の AC-1〜AC-3 をすべて満たし、テストが通り、PR を出して管理役へ報告した`
  - `delegate_task` の依頼文に書いても効かない（T3 が先頭に別の文を足すため、ただの文章になる。2026-11-13 に確認）。立てたあと、その子へ `t3_thread_send` で `/goal …` だけを1通送る。Codex・Claude ともこの形で効くことを確認済み。
  - 使うのは Issue の担当だけ。要件を詰める・Issue の案の承認待ち・検証役には使わない（本人の答えや承認を待たずに進んでしまうため）。
  - Codex のゴールは、止めたり条件を満たさずに終わると一時停止になる（`/goal resume` で再開）。担当は Sol（Codex）なので、担当の進みが止まったら管理役が理由を確かめ、続けてよければ `/goal resume` を送る。Claude のゴールは止めても残る。終わった・やめるときは `/goal clear`。
- 同じ Issue の修正・続きは、同じサブエージェントに `t3_thread_send` で戻す。同じ Issue に担当を2つ作らない。
- 途中でまったく別の要件が出たら、担当は広げず管理役へ返す。管理役が Issue の案を作って本人に見せる。

### まとめる前（並列の PR）
- Issue ごとに worktree と PR を分け、基本は並列のまま進める。
- 1つ merge されるたびに、残りの PR は最新の main を取り込み、衝突を直し、SWE-2 Flash・high がテストを走らせ直す（文字の衝突が無くても、合わせると動かなくなることがあるため。Devin Review などは取り込み前の食い違いに気づけない）。
- 同じ画面や同じ処理を大きく作り替える Issue 同士だけ、順番にやる。
- merge の前に、PR の自動チェック（Devin Review、Amazon Q）の完了を待ち、レビュー本文を読む。`gh pr checks <番号>` を10〜15秒おきに見て、終わったら `gh pr view <番号> --json reviews,statusCheckRollup` で読む。指摘が残っていれば merge しない（古い行への指摘も、中身がまだ当てはまるなら未解決として扱う）。
- SWE-2 の子は PR を T3 のスレッドにリンクする道具を持たないので、管理役がリンクする。
- **本番のブランチ（`main`）への merge は本人が決める。** 確認用のブランチ（リポジトリごとに1つ。名前の既定は `dev`）への merge は、テスト・レビュー・必要な独立の検証がすべて通ったら、管理役が自分でしてよい（本人の決定 2026-11-12）。確認用のブランチが無いリポジトリでは、最初に作ってよいかを本人に聞く。

### セキュリティのスキャン（Devin Security 2.0。本人の指定 2026-11-12）
Devin Security 2.0 は、リポジトリ全体を脅威モデルに沿って調べ、見つけた弱点を再現して確かめるスキャン。PR ごとの Devin Review とは別物で、PR 単位では走らせない。管理役が API で走らせ、結果を読む（課金がからむので子には任せない）。

**依頼時の選択ルール（本人の指定 2026-11-14）**: Devinでのセキュリティ調査・レビュー・スキャンを依頼された場合は、Devin Security 2.0の正式なcode scanを使う。通常のDevin/SWE-2子の静的監査やPRのDevin Reviewを代用しない。正式機能を利用できない場合は未実施と理由を返し、静的監査で代替完了にしない。これは通常のPRレビュー全般をcode scanへ変更するルールではなく、スキャン実行・追加費用の許可でもない。以下の実行承認・対象repo/固定SHA・`effort: normal`・脅威モデル・予算/権限・既存スキャン状態・secret非表示の確認を省略しない。

**走らせるとき（どれかに当たれば、本人に聞かずに走らせてよい）**
- `main` への merge を本人に頼む前で、前回の完了したスキャンのあとに「セキュリティに関わる変更」が確認用のブランチに入っているとき。セキュリティに関わる変更とは、認証・権限、課金、secret・環境変数、外から入力を受ける API、ファイルの受け取り、DB の問い合わせ、依存パッケージの追加・更新。
- `main` への merge を本人に頼む前で、前回の完了したスキャンから14日以上たっているとき。

**走らせないとき**
- 同じリポジトリで、前のスキャンから7日たっていないとき（本人が頼んだ場合は別）。
- 文書・見た目だけの変更しか入っていないとき。
- 前のスキャンがまだ動いているとき。

**本人に聞いてから**
- そのリポジトリの初回のスキャン、`effort: deep` のスキャン、見つかった弱点を Devin に直させる操作（Fix with Devin / remediate）。どれも費用が大きくなりうる。

**走らせ方**
- 対象は確認用のブランチの先頭の commit（`commit_sha` で固定）。`effort` は `normal`。プロファイルは名前が「<SECURITY_THREAT_MODEL_NAME>」のものを一覧から探して `profile_id` に入れる。
- 鍵ファイルは `DEVIN_API_KEY_FILE`、組織 ID は `DEVIN_ORG_ID` で指定する。鍵の値は表示しない・Issue や PR に書かない。
```bash
bash -c 'ORG="$DEVIN_ORG_ID"
B="https://api.devin.ai/v3/organizations/$ORG/code-scans"; H="Authorization: Bearer $(cat "$DEVIN_API_KEY_FILE")"
curl -s -H "$H" "$B/profiles"                                   # profile_id を探す
curl -s -H "$H" "$B/scans"                                      # 前のスキャンの日付と状態を見る
curl -s -X POST -H "$H" -H "Content-Type: application/json" "$B" \
  -d "{\"repo_name\":\"<owner/repo>\",\"profile_id\":\"<id>\",\"commit_sha\":\"<SHA>\",\"effort\":\"normal\"}"
curl -s -H "$H" "$B/findings?scan_id=<scan_id>"                 # 終わったら結果を読む'
```
- 始めたら `scan_id` と対象の commit を Issue（無ければ報告）に書く。待つ間はほかの仕事を続け、`scans` の `status` が `completed`・`failed`・`cancelled` になったら読む。`409` は混雑なので時間をおく。
- zsh では変数名に `path` を使わない（PATH が壊れる）。上のように `bash -c` で包む。

**結果の扱い**
- `severity` が `high` 以上で `status` が `open` のものが1件でもあれば、`main` への merge を本人に頼まない。内容をまとめ、直す Issue の案を本人に見せる。
- `medium` は内容を報告に書き、直すかどうかを本人に聞く。`low` は件数だけ書く。
- スキャンが `failed` のときは1回だけやり直す。それでもだめなら「未検証」と書いて本人に伝える。スキャン済みとして数えない。
- 直しは通常の流れ（Issue → 担当 → レビュー → 検証）で行う。Devin が出した修正 PR をそのまま merge しない。
- 本人への報告には、スキャンの対象の commit、`effort`、件数（high / medium / low）、残っている指摘、スキャンを走らせたこと（費用が発生したこと）を書く。

### 検証と受け入れ
- **順番を守る: 担当のテスト → 自動レビューが落ち着く → 最後の版に独立した検証を1回。** 自動レビューの直しが終わる前の版に検証をかけない（直したあとに、もう1回立てることになる。2026-11-12 は5つの Issue で検証役が20本になった）。
- 中・大の Issue には、管理役が検証役を立てる（担当に選ばせない）。渡すのは PR・対象の commit・受け入れ条件だけ。担当のまとめ文は渡さない。
- 検証役への依頼文に入れること: 対象の commit の SHA、確かめる範囲（小さく切る。長い記録は必要な行だけ読む）、立てたサーバーは終わる前に止める、最後の行は「判定: …」の形で書く。「判定:」の行が無い結果は、合格として扱わない。
- 検証で不合格が出て担当が直したあとは、直した部分だけを確かめる検証を1本。全体をやり直さない。
- 受け入れは、担当の報告と検証役の判定で決める。同じ読み込みやテストを繰り返さない。根拠の不足・食い違い・対象の版の変更があるときだけ差し戻す。

### 本人への報告
- 完了の節目は、聞かれる前に短く出す（一部完了＋残りも）。「○○についてです」で始め、3〜4行。何ができたか・残りと次にすること・Issue と全体ボードのリンク。デザインの Issue は変更前と変更後の画面を付ける。
- 報告だけなら返事を求めず次へ進む。
- **並列で動かしている間、本人に送るのは区切りだけ**: 確認用のブランチに入った／止まった／本人に決めてほしいことがある。担当や検証役から知らせが届くたびに、本人へ書かない（2026-11-12 は細かく長い知らせが20通以上になり、本人が状況を3回聞き直した）。
- 状況は、Issue ごとの1枚の表で見せる（列: Issue／いまの段階／PR／残り）。段階は「実装中 → 自動レビュー → 検証 → 取り込み済み」。区切りの知らせにはこの表を付け、聞かれたときもこの表で答える。
- 状況を聞かれたら、対象の Issue の最新コメントを読んで答える。読んでいなければ「未確認」と言う。

### リポジトリを離れるとき
- しばらく触らなくなったら、管理役のセッションは完了にする。中身はファイルと Issue にあるので、また使うときに新しいセッションを立てて読み直せる。

## 枠を減らさない動かし方（キャッシュを効かせる）

読み直しは、キャッシュが効いていれば安い（Opus で新しく読む時の約20分の1）。切れると、会話の全部を高い値段で書き直すことになる。次を守る。

- **自動の要約を早める設定が入っている**（本人の決定 2026-11-12）: `~/.claude/settings.json` の `autoCompactWindow: 200000`。Claude のセッションは、会話が約20万トークンになると自動で要約して縮む（前は100万まで膨らんでいた）。要約で細かい話は落ちるので、決めごとは必ずファイルと Issue に書く。忘れっぽいときは、本人に相談して数字を上げる（10万〜100万）。
- **会話を短く保つ**: いちばん効く。セッションは替えない（本人の決定 2026-11-12。切り替えは手間なのでやめた）。大きなファイルや長い記録を読む仕事は子に渡し、親は結論だけ受け取る。長い出力は必要な行だけ読む（`limit`、`jq`、`grep`）。
- **起きる回数を減らす**: 1回起きるたびに全部を読み直す。知らせは区切りだけ。独立した道具の呼び出しは、1回にまとめて並べて出す。
- **間をあけて細かく起こさない**: キャッシュは一定の時間（5分〜1時間）で切れる。切れたあとに起きると、全部を書き直す。待つなら、子の完了の知らせで1回だけ起きる。短い間隔で見に行く（ポーリング）のも、長くあけて何度も起きるのも避ける。
- **途中でモデルを替えない**: キャッシュはモデルごと。替えると全部を書き直す。別のモデルが要るときは、子に渡す。
- **途中で土台を変えない**: 動いているセッションの最中に、共通ルール（`AGENTS.md`）・道具（MCP）の入れ替えをすると、先頭から書き直しになる。こうした設定の変更は、区切りにまとめる。
- **定期的に動かす仕事は、毎回新しい会話で**（`freshSession`）。前の回の会話を引きずらない。
- **CEO（Sol・xhigh）は短い相談と振り分けだけ**。調査・設定・長い作業は、Opus の別セッションか子に渡す。

## Issue の担当（サブエージェント）

- 着手前に自分で確かめる: Issue の番号・URL・OPEN、目的・範囲・対象外・受け入れ条件・確かめ方、最新の承認と止まっている理由。分からない承認は推測で埋めず、管理役へ返す。
- 既存の実装・スキル・公式の機能を先に調べる。新しい依存や自作は、足りないと確かめたものだけ。
- 最新の main・作業ブランチ・未コミットの差分を確かめ、自分の worktree とブランチで作業する。ブランチと Issue の対応は Issue に書く（T3 がブランチ名を付け替えることがあるため）。
- 画面は Claude / claude-fable-5-2・中 に、それ以外の実装は Codex / gpt-6.1-terra・high（大は max）に、テストを書くのは Terra・max に、走らせるのは SWE-2 Flash・high に、小さな修正・一括作業は SWE-2・max に、短い指示で渡す。Terra・SWE-2 の差分は Claude / claude-sonnet-5-5・low にレビューさせ、画面の差分は自分で見る。合否は自分で決める。自分は判断（要件・振り分け・指示・合否・報告）だけをし、コードは小さい直しも書かない: 画面は同じ Issue の Fable・中のスレッドへ（終わっている・ない・会話が長すぎるときは新しい Fable・中の子へ）、画面以外は直し方が決まっていれば SWE-2・max へ、原因や直し方が決まっていなければ Terra・high へ、検証用の fixture・台本は Terra・max へ渡す（管理役が担当を兼ねるときも同じ。途中で別の不具合が見つかったら、それも渡す）。2回不合格なら Fable・高 へ渡し、その旨を Issue に1行残す。
- テスト: 受け入れ条件に結び付けて、種類（Unit/Integration/E2E/lint・typecheck・build・security）と環境を選ぶ。対象の commit・データの区分（fixture/mock/実データ）・環境・コマンドを固定する。書くのは Terra・max、走らせるのは SWE-2 Flash・high（Codex が上限なら書くのも SWE-2）。どちらも使えなければ自分で走らせ、その旨を Issue に書く。
- 未実行は「非該当／blocked／未検証」を分けて書く。失敗を skip に変えて成功扱いしない。通すためにテストを弱めない。図や静止画を E2E の証拠にしない。途中でコードを直したら対象の commit を取り直す。iOS の画面操作は Maestro を使う。
- 節目（着手・PR 作成・完了・詰まったとき）で Issue にコメントし、ボードの段階を更新する。
- PR: 作業ブランチへの commit・push と Draft PR は自分で進めてよい（依頼文で許されている範囲で）。保護ブランチへ直接 push しない。merge・deploy はしない。
- 本人の判断が要るときは、質問用の道具で聞く（管理役が拾って本人に出す）。影響しない作業は続ける。
- 完了時: Issue コメントに、受け入れ条件ごとの結果（コマンド・対象の commit・結果・未実施の層）＋残り＋本人向けの短文1〜3行。管理役へ「対象の版・判定・残り」を返す。
- 検証役の指摘は同じ担当として直す。当たらない指摘は根拠を残す。直したあとの head で確かめ直し、古い合格を使い回さない。
- 範囲外の課題、道具の不具合は、回り道せず管理役へ返す。

## 検証役

- E2Eはすべて実行ごとに録画し、失敗・中断・再実行もprivateな証跡として保存する。管理役・担当は実行を渡す依頼文にこの条件を含め、検証役は動画の保存と読戻しまで確認する。詳細は `test-case-board/references/e2e-recording.md`。録画不能・保存未達はテスト成否と分けて報告し、過去の未録画を録画済みとしない。

- 自分が作ったものを独立検証済みにしない。作った側と別の会社のモデルで行う。
- 対象の変更・commit と差分・受け入れ条件・既存の検証結果を読む。主張をそのまま採らず、確認やテストで根拠を確かめる。
- 検証する commit の SHA を固定する。途中で変わったら判定をやり直す。
- 合格・不合格・未検証を分ける。指摘には対象の箇所・影響・確かめ方を添える。
- 検証に要る実行だけ行い、製品コードの修正・公開・merge はしない。修正は同じ担当へ戻す。
- 修正後は変わった所と影響する範囲だけ確かめ直し、変わっていない層の有効な検証は引き継ぐ。
- 結果は同じ Issue に: 対象の版／行った確認／判定／指摘／未検証のこと。
- 既存の不合格・失敗・未検証を消さない。コメントの解決だけで合格にしない。2回不合格なら本人へ。
