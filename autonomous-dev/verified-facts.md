## 確かめたこと（2026-11-12）

- CEO（Fable）が `t3_thread_launch` で Opus・中の新しいセッションを立てられる。
- セッションは自分の名前を `t3_thread_update`（`action:"rename"`）で後から変えられる（`準備 | …` → `Issue #… | …`）。
- 終わったサブエージェントに `t3_thread_send` で続きを送ると、前の会話を覚えたまま続けられる（SWE-2 の子で確認。threadId は返ってきたリンクの中の、`%3A` が入った形をそのまま使う）。確かめたのは十数分後まで。
- 並列で動く: `delegate_task` を `mode:"async"` で3つ立てると同時に動いた（SWE-2 Flash 2本と Haiku 1本、開始時刻が2秒以内）。`mode:"wait"` で並べると1つずつ順番になる。並列にしたいときは必ず async。親は待つ間も本人と話せ、終わるたびに1回起こされる。
- 並列で実装できる: Opus の管理セッションから SWE-2 を5つ、`mode:"async"`・`isolation:"worktree"` で立てると、5つが別々の作業フォルダ（`~/.t3/worktrees/<repo>/t3-…`）と別々のブランチで同時に書いてコミットした（約1分、上限には当たらず）。ブランチ名は T3 が途中で自動で付け替える（`t3/<内容>`）ので、Issue 番号とブランチの対応は Issue に書く。同じファイルの同じ場所を触ると、まとめるときに衝突する。扱い（本人の指摘 2026-11-12）: 基本は並列のまま、Issue ごとに worktree と PR を分ける。1つ merge されるたびに、残りの PR は最新の main を取り込み、衝突を直し、SWE-2 がテストをやり直す。同じ画面や同じ処理を大きく作り替える Issue 同士だけ、順番にやる。
- PR を並列で出してまとめるところまで通る: 管理役が SWE-2 の子2つに `t3_thread_send` で続きを頼み（前の会話・作業フォルダを覚えていた）、それぞれ push と PR 作成 → 1つ merge → もう1つが衝突状態 → 子が最新 main を取り込んで直しテストをやり直す → merge。再試行なし。注意: SWE-2 の子は PR を T3 のスレッドにリンクする道具を持たないので、管理役がリンクする。merge のコミットはエディタが開けないので `--no-edit` を付ける。
- 成果物は localhost で見られる: サブエージェントが自分の作業フォルダでサーバーを裏で立てる（`nohup … &` と `disown`）と、サブエージェントが終わったあとも残り、どのセッションからも `<ローカルプレビューURL>` で開ける。ポートは Issue ごとに変える（例: 3100 + Issue 番号）。Issue が終わったら止める。（※ 下の「サーバーを残させるとき」の記録で、`nohup … &` では止められることがあると分かった。いまは `setsid` か `start_new_session=True` を使う。）
- 合わせると動かなくなる食い違いは、取り込み直しのテストで拾える: 片方が関数名を変え、もう片方が古い名前で呼ぶ2つの PR は、文字の衝突なし（MERGEABLE / CLEAN）だったが、最新 main を取り込んだ直後のテストが失敗し、子が直して通した。Devin Review と Amazon Q は、取り込み前の時点ではこの食い違いに気づけない。
- merge の前に自動チェックを待つ: `gh pr checks <番号>` を10〜15秒おきに見る。Devin Review は約30秒、Amazon Q は約15秒で終わる。終わったら `gh pr view <番号> --json reviews,statusCheckRollup` でレビュー本文を読む。指摘が残っていれば merge しない（古い行への指摘も、中身がまだ当てはまるなら未解決として扱う）。Amazon Q は push し直した後には動かないことがある。
- サブエージェントの質問は管理役のセッションで本人に出せる（本人の指定: 必ず質問コンポーネント `AskUserQuestion` を使い、頭に `[Issue #N]` を付ける）。流れ: 子が質問用の道具で聞く → 管理役が `t3_pending_request` の `list` / `read`（threadId は子）で中身を読む → 自分のセッションで `AskUserQuestion`（複数の子の質問は1回にまとめる）→ `respond` で子に返す。Claude の子は質問で止まると管理役に知らせが来るが、Devin（SWE-2）の子は知らせが来ない。子を待つ間に起こされたら、動作中の子すべてに `list` をかける。
- 片付け: 終わった Issue は `git worktree remove` と `git branch -D`（merge 済みはリモートのブランチも）で消せる。子のスレッドの記録は片付けたあとも読める。T3 の作業フォルダ一覧（`t3_worktree_list`）には古い表示が残る。
- サブエージェントにサーバーを残させるときは、`nohup … &` では子のコマンドが終わると止められる。`setsid` か Python の `start_new_session=True` で別セッションとして起動させる。
- 新しいセッション（`t3_thread_launch`）や既存セッションへの依頼（`t3_thread_send`）は、終わっても依頼元に自動では知らせが来ない（`delegate_task` の子だけ自動で来る）。依頼文に「終わったとき・止まったときに `t3_thread_send` で知らせる」と書くと、知らせが届く（2026-11-12 に確認）。
- スキルを自分から読むか（2026-11-12、同じ開発の依頼を各5回）: Codex と Grok は5回とも最初に `autonomous-dev` を読んだ。Claude（Opus）は、共通ルールに「最初の操作として本文を開く」と書く前は0回、書いたあとは5回とも最初に読み、Issue の案を出して承認を待った。Devin（SWE-2）は書いたあとも、読みはするが5回中3回は「自分は子だ」と判断して承認なしで実装した（worktree や `t3/` で始まるブランチ名を根拠にする）。だから SWE-2 は直接の開発セッションに使わず、必ず子として範囲つきで頼む。
- 道具でセッションを立てるときの注意: `create_threads` は、指定したプロジェクトではなく呼んだ側の作業フォルダで動いた。別のリポジトリで動かしたいときは `t3_thread_launch` に `projectId` と `workspaceStrategy` を付け、まず1つ立てて `pwd` と `git remote` を確かめてから残りを立てる。確かめずに立てて、本物のリポジトリに Issue と PR が作られる事故が起きた。
- 3つ重ねて呼べる: 左のセッション → Opus のサブエージェント → SWE-2 のサブエージェント。
- `t3_thread_list` に `includeSubagents:true` を付けると、サブエージェントも一覧に出る。親の ID（parentThreadId）、状態、モデル、リンクが付く。看板はこれで作れる見込み（看板に出す画面は、まだ無い）。
- Opus の担当セッションから `delegate_task` で SWE-2 を子として呼べ、担当と同じ作業フォルダで動く。
- Devin が「実行ファイルが入っていない」で起動できないときは、T3 Code の設定で Devin の実行ファイルの場所（Executable override）を `~/.local/bin/devin` に向ける（2026-11-12 にこれで直った）。
